# 0.2.0-dev · 2026-08-06

[English](2026-08-06.md) · [中文](2026-08-06.zh-CN.md) · [Release index](README.md)

This development snapshot closes the scientific-gate and state-recovery gaps identified by the ninth code review.

## Scientific gates

- External-result contracts now bind each registered evaluator's callable identity, evaluator-contract version, and packaged source digest. Those fields enter the structured gate result and its receipt identity.
- `requires_review` and `not_evaluable` accept manual adjudication only; invented automatic-evaluator metadata cannot convert either status into acceptance.
- When a registered evaluator returns `failed`, the execution receipt, reloaded negative artifact, and exact automatic rejection are preserved. A major or fatal review must then choose exclusion, rerun, method change, or another non-retain action.
- A container or scientific-family admission failure rolls back content-addressed objects created by that ingest transaction and leaves no orphan payload.

## Research plans and state recovery

- Review-triggered rerun and method-switch actions now have a public preparation path. A registry-validated child plan freezes a node-level revision contract before the scientific decision; all outputs from the source execution must share its action, target, and request identity. Structured parameter changes execute through the same normalized request identity used by command modules, and untouched downstream work is rebound to the replacement outputs.
- A real public FastQC scenario now covers initial execution, review, adjusted-parameter revision preparation, replacement admission, decision, rerun, second review, retention, and subsequent project continuation.
- Project state advances to schema v2. A real v1 state produced by commit `10bafce`, containing three gate adjudications, is retained as a regression fixture. Migration verifies its digest and event chain, recovers added fields from the original receipts, and records the source digest and event count.
- Map-bound v1 states now use a non-overwriting migration command that verifies the immutable publication store and records the old maps as inactive historical lineage. A new map must explicitly continue the verified parent before formal delivery resumes; ambiguous or tampered state or map bytes remain blocked.

## Journal catalog

- The catalog index now distinguishes `draft` and `released`. Catalog `2026.08.03` is explicitly a development draft; drafts may be corrected, while a released version becomes byte-immutable and later changes require a new version.

## Verification

- Lightweight counterexamples cover forged automatic adjudication, registered evaluator failure, exclusion after failure, object rollback, invalid or split-brain rerun targets, live-registry drift, public review-to-rerun reachability, map-bound v1 migration and republication, immutable-map tampering, and journal-catalog lifecycle.
- No large public-data analysis or new public-data download was performed.
