# 开发与发布

本指南面向维护者和扩展 Biomed Workbench 的 Agent。用户安装和研究使用分别见[安装](installation.zh-CN.md)与[使用指南](using-biomed-workbench.zh-CN.md)。

## 开发原则

- 先核实真实仓库、当前注册表、测试、报告和工作区状态；
- 以完整科学契约新增模块，不以工具名称堆砌能力；
- 项目差异进入封闭参数、配置和产物绑定，不能要求用户修改模板源码；
- 官方手册决定 API 和可调参数，方法论文与代表性研究决定适用场景和结果展示；
- 运行计划不是科学证据，只有真实执行、结果重读和质量评审后的产物才能进入证据地图；
- 注册表、科学执行器、运行依赖和说明文档分别版本化。全局注册表或文字分类变化只重建确定性索引；模块范围元数据变化先审查并换发证据范围；运行依赖变化做针对性兼容复验；只有科学执行器、参数语义、输入处理或结果识别发生变化时才重新计算。禁止因全局摘要变化盲目重跑，也禁止在科学实现已变化时只换绑旧报告；
- 模块的第一分类字段只承担路由；尺度、测量家族和工具角色由独立科学分类报告核对，不能靠宽泛关键词制造虚假流程。
- 方法别名、排除语境、必要上下文、具名方法优先级、科学阶段和上游评审要求必须写在模块清单中；路由器不能按模块标识写特殊判断，研究计划也不能另存一份阶段表。
- 路由与编排字段只影响发现和计划编译，不进入科学执行证据范围；修改这些字段不能使旧科学结果失效，也不能把旧结果换发成新执行证据。
- 外部工作流必须把“文件与科学家族准入”同“逐条科学质量门评定”分开。前者核对真实文件、身份、账目和家族不变量；后者把每条门唯一分配给能够提供证据的输出端口。门禁名称不能触发自动通过；只有为该门显式登记的专属评定器完整重算了声明中的观测项，才能作为系统来源结论。其余门一律记录为“需要科学复核”，不能由文件可读性代替。
- 外部结果准入契约使用独立的协议版本和交接校验身份。集中式协议注册表当前只支持 `2.1.0`；交接创建、状态载入、事件重放和结果接收均拒绝未知版本或旧版本，不能通过版本不匹配静默降低检查强度。协议冻结排序且不重复的完整门禁集合及其摘要，并绑定每个登记评定器的可调用身份、评定契约版本和插件内程序摘要；回执必须同时保存每个门禁的结构化结果和对应校验值。评定器真实返回“失败”时，产物仍会完成重读并作为负向产物登记，系统只能依据同一登记评定器生成“自动拒绝”；“需要科学复核”和“当前不可评定”只能人工审议，调用方伪造自动评定器字段不能放行。产物导入采用事务：容器或科学家族准入失败时，新建对象随事务回滚，不留下无状态引用文件。每个待复核门禁必须形成绑定具体执行回执、输出端口、观测值、冻结判定标准、具体发现、结果摘要和证据文件的独立科学审议。完整审议集合允许负结果进入严重或致命等级评审，但只有已接受门禁可以被保留；拒绝或未解决的门禁只能进入排除、重跑、换方法、补数据、修订计划或停止分支。产物评审、科学决策、交付范围与证据地图继续绑定该审议集合。收紧准入边界会改变后续交接，但不会把方法、模板、参数和依赖均未改变的既有公共数据计算伪装成重新执行。
- 重跑与换方法在产物评审之后、科学决策之前，通过实时注册表创建不可变的子计划。节点级修订契约固定来源与目标节点、动作、两个方法清单的校验身份、登记替代关系、输入输出契约、原执行与新执行的请求身份、结构化参数调整和科学理由；同一来源节点的全部输出必须共用同一契约、动作、目标和请求身份。原方法原参数重跑保持实际请求身份不变，调整参数重跑在命令参数规范化后登记不同身份，换方法必须使用模块清单声明且端口兼容的不同方法；未执行的下游节点改接到新产物，替代节点执行前需重新完成分析准入。公开的 `prepare-revision` 路径和真实命令模块端到端测试共同验证评审到重跑的完整链路。
- 项目状态 schema v2 保存迁移来源。校验完整的 v1 状态只有在新增门禁字段能从原执行回执精确恢复时才会重放迁移，并保留旧状态校验值和事件数。已经绑定旧证据地图的 v1 状态使用独立的 `migrate-state-v1` 路径：先验证不可变地图目录，再写入不同路径的 v2 状态，不覆盖旧文件；旧地图作为已验证历史保留，但只有新地图明确延续其父版本并绑定迁移后状态，才能恢复正式交付。
- “存在测试案例”与“案例已经执行并重新读取”是不同的就绪维度；进程 JSON 往返和序列化产物文件重读也分别报告。隔离执行收据必须记录模块版本、兼容性组合、案例校验值、完整规范化输出校验值、验收投影校验值、实际运行版本、重读方式和往返类型。
- 公开执行入口必须同时绑定现有项目目录、完整项目背景、假设、输入产物、分析准入和明确的兼容性组合；不存在只提交一段 JSON 就把科学模块标记为完成的宽松入口。
- Codex 是当前完整验证的参考宿主；其他智能体可以通过独立适配层读取现有技能、注册表、路由和 runner，但不得把入口兼容表述为全流程认证，也不得为了宿主兼容而改写科学模块、模板、质量门控或旧验收报告。

## 主要目录

- `skills/biomed-workbench/`：唯一用户入口；
- `biomed_workbench/modules/builtin/`：独立科学模块；
- `biomed_workbench/capabilities/`：项目自有实现；
- `biomed_workbench/kernel/`：项目状态、证据、评审与决策；
- `biomed_workbench/orchestration/`：规划、执行和质量控制；
- `biomed_workbench/services/`：受限公共数据库客户端和凭据策略；
- `tests/`：单元、契约、集成、发布与端到端验证；
- `reports/`：可公开的当前验证证据。

## 发布门禁

发布前必须重新生成模块索引、能力目录、执行就绪审计、实验模块成熟度、公共案例与全局证据绑定；随后完成受影响测试、完整测试和发布验证。凭据、私有路径、临时文件、开发桥接、过期摘要和未绑定报告都会阻止发布。

每份真实运行证据在发布前先经过重验证分类：执行代码校验值改变时重新计算；隔离环境或依赖范围改变时只复验受影响运行层；模块说明或成熟度改变时审查并换发模块范围；README、全局索引或无关模块新增不触发科学重算。`tools/assess_report_revalidation.py` 将这一判断落实为机器门禁并给出可复用、需元数据审查、需兼容复验或需重算四类结论。

Codex 与可选适配器的边界通过 `tools/audit_adapter_boundaries.py` 和 `reports/adapter-boundary-audit.json` 进入发布门禁。`access: codex_native` 继续表示 Codex 原生交接；其他宿主只有经过独立验证的等价实现才能完成该节点。适配器验收、安装身份和科学证据身份分别管理，适配器变化不能提高模块成熟度或触发旧科学结果换绑。

内部命令与完整维护流程见 [Development and Release](development.md)。
